# ETH/UCY 训练吞吐提速方案

_基于 2026-09-05 至 2026-09-06 Missing-Aware 第一组实验（M0/M1/M2、`random_fixed4_ng`）的实测结果；2026-09-11 补充数据管线拆解，修正 §1 的 DataLoader 结论。_

## 1. 实测结论

| GPU 状态 | 实测速率 | 结论 |
|---|---:|---|
| 单任务独享 GPU | 约 `26 s/epoch` | 当前基线 |
| 两个任务共卡 | 约 `105 s/epoch` | 慢约 `4×` |
| 三个任务共卡 | 约 `160 s/epoch` | 慢约 `6×` |

当前最主要的问题是 **GPU 共卡竞争**，不是模型结构或数据集规模。fold ETH 训练集有 `30,307` 个样本、每 epoch `474` 个 step；模型约 `5.7M` 参数，batch size 为 `64`。

此前测试还表明：

- `num_workers=4` 调整到 `16` 没有明显提速——此结论的**原因解释已修正**，见 §1.2，不是"DataLoader 没问题"；
- 独享 GPU 时仍存在明显的 CPU dispatch、kernel launch 和优化器开销；
- 当前没有足够证据支持直接改模型执行引擎。

### 1.1 当前架构实测诊断

在空闲 GPU 上使用当前 Clean-direct 配置（`M0`、`num_modes=20`、`batch_size=64`、`bf16`、`bimamba=true`）复测得到：

- 数据读取平均约 `48.6 ms/batch`（该数字在空闲机器测得；其内部构成见 §1.2，主要被 `torch.load` 主导）；
- forward + loss 约 `69~79 ms/batch`；
- backward + optimizer 约 `126~156 ms/batch`；
- 总训练 step 约 `195~234 ms`，按 `474 steps/epoch` 折算约 `92~111 s/epoch`；
- profiler 记录 CUDA 实际时间约 `70.8 ms`，CPU self time 约 `278.7 ms`，说明当前不是单纯的 GPU 算力不足；
- `cudaLaunchKernel` 约 `7,861` 次、CPU 时间约 `41.5 ms`；`SelectBackward` 约 `35.6 ms`；AdamW step 约 `27.4 ms`。

从参数规模看，`TimeDecoder` 约 `4.10M` 参数（`71.9%`），Scene Transformer blocks 约 `0.99M`（`17.4%`），历史 Mamba 约 `0.54M`（`9.5%`）。因此 TimeDecoder 是主要结构成本，但这不等于可以在正式实验中删层、改宽度或替换模块；这些修改会改变方法和模型能力，当前不纳入提速方案。

`num_modes` 不是当前第一优先级：`6 modes` 约 `172 ms/step`、`81.6 s/epoch`，`20 modes` 约 `195 ms/step`、`92.4 s/epoch`，从 6 增加到 20 只增加约 `13%`。因此不应通过减少 mode 数换取速度，也不能把当前 `num_modes=20` 的 `92~111 s/epoch` 与历史 `6 modes` 的 `26 s/epoch` 直接比较。

### 1.2 数据管线拆解（2026-09-11 修正）

对 fold ETH train（30,307 样本）的 `EthUcyBenchmarkDataset.__getitem__` 逐环节计时，单样本 CPU 耗时分布：

| 环节 | 耗时/样本 | 占比 |
|---|---:|---:|
| `torch.load(weights_only=False)` | ~13.7 ms | ~50% |
| `process()` 合计 | ~5.2 ms | ~19% |
| └ `build_b1_motion_features`（逐 actor 循环） | ~1.2 ms | — |
| └ `build_missing_features` | ~0.26 ms | — |
| └ float64 旋转 | ~0.03 ms | ~0.1% |
| `__getitem__` 总计 | ~27 ms | 100% |

由此修正两处既有判断：

1. **"DataLoader 不是瓶颈"不成立。** 数据管线单样本约 `27 ms` 里，约一半是 `torch.load(weights_only=False)` 的 pickle 反序列化（每个 `.pt` 一个样本，`__getitem__` 每次访问都重新 load，每 epoch 3 万次、100 epoch 就是 300 万次）。实测 `weights_only=True` 加载快 **28×**（`13.7 ms → 0.49 ms`）。`num_workers 4→16` 不提速的原因不是"管线没问题"，而是单样本工作被 `torch.load` 的 pickle 主导，加 worker 无法分摊这部分按样本串行的反序列化开销。

2. **float64 旋转不是问题。** 实测 `~0.03 ms/样本`、占 `0.1%`，属噪音，不列入提速清单。

**口径警告（重要）**：上表绝对值在 CPU 高负载机器上测得（`uptime` load average ~83，存在占 40+ 核的外部进程与跨天满核进程），绝对值偏高，不能直接折算成"每 epoch 慢 X 分钟"。§1.1 的 `48.6 ms/batch`（≈ `0.76 ms/样本`）很可能在空闲机器测得，与本表的 `27 ms/样本` 相差约 `35×`，此差距主要来自外部 CPU 争抢。**负载无关的稳定结论只有两条**：(a) `weights_only=True` 相对 `False` 的 28× 相对加速；(b) `torch.load` 是数据管线最大单项。若要对各环节做正式定价，须在独占且 CPU 空闲的机器上重测。

## 2. 当前采用的优化

### 2.1 GPU 独占

这是当前收益最高、风险最低的优化，也是正式实验应立即采用的执行方式。

- 一张 GPU 同时只运行一个 DeMo 训练任务；
- 不与 vLLM、其他训练任务或大型推理任务共卡；
- 五折可以并行，但应做到一折一张独占 GPU；
- 启动训练前用 `nvidia-smi` 检查目标 GPU 没有外部进程；
- 不要把多个 fold 挤到同一张 GPU 上。

这只改变任务等待时间，不改变数据、模型、loss、梯度、optimizer 更新或 checkpoint 选择，因此不改变模型能力和正式实验结论。

**已观测收益**：从共卡恢复到独享，墙钟时间预计改善约 `4~6×`。

### 2.2 数据管线：`weights_only=True`

`torch.load(weights_only=False)` 是数据管线里最大单项（见 §1.2），改为 `weights_only=True` 实测 28× 加载加速，且加载的是同一份 tensor、不改动任何数值路径，属零风险纯收益项：

- `ethucy_dataset.py:59`（以及其它 dataset 的 `__getitem__` 里的 `torch.load`，含已删除的旧 benchmark dataset）将 `weights_only=False` 改为 `weights_only=True`；
- 前置校验：确认所有 `.pt` 只含 tensor 与基本类型（不含自定义类实例），否则 `weights_only=True` 会加载失败；
- 改动后跑 `tests/` 与单 fold 首 epoch，校验字段、loss 与指标数值一致后再推广到正式实验。

### 2.3 减少日志同步开销

当前训练每个 batch 记录多个 loss，并在单 GPU 下使用 `sync_dist=True`。`cal_loss()` 还会多次调用 `.item()` 生成日志标量，这可能造成不必要的 GPU-CPU 同步。

下一轮训练可以做以下工程修改，但只在不改变 loss、指标和 checkpoint 选择逻辑的前提下进行：

- 单 GPU 训练将训练日志的 `sync_dist` 改为 `False`；
- 保留现有日志字段和监控指标，减少不必要的 step 级日志刷新；
- 保留 loss 计算和返回给 Lightning 的 tensor，不让日志值参与 loss 或梯度计算；
- 移除仅用于日志的 `.item()` 同步，但保留相同的日志字段；
- 保留 `val_minFDE20` 监控和 best/last checkpoint 逻辑（主链 K=20；历史 `val_minFDE6` 口径已废弃）。

这类修改只影响日志和同步，不改变模型前向、loss 数值定义或反向传播。

**预期收益**：小到中等，具体收益需要在独享 GPU 上实测；它不是当前主要的 `4~6×` 加速来源。

### 2.4 DataLoader 资源控制

保持单任务 `num_workers=4`、`pin_memory=True`，不改变 sampler、shuffle、batch size 和样本处理逻辑；多任务并行时不要继续扩大 worker 数。

在独占且 CPU 空闲的机器上，应先落 §2.2 的 `weights_only=True`，再复测 worker 数是否有收益——此前 `4→16` 不提速的结论是在 torch.load 主导 + 机器 CPU 争抢的干扰下得到的，不能据此断定 worker 数无优化空间。

### 2.5 当前架构的优化优先级

结合 profiler、对照实验与 §1.2 数据管线拆解，优先级固定为：

1. **P0：GPU 独占。** 共卡/独卡对照直接验证的主收益来源，预计约 `4~6×` 墙钟改善。
2. **P1：`weights_only=True`。** 数据管线最大单项，28× 加载加速、零数值风险，收益直接。
3. **P2：日志与同步清理。** `.item()` 与单卡 `sync_dist=True`，小到中等收益，不改变模型计算图。
4. **P3：循环向量化 + 预处理缓存。** `process()` 里的逐 actor Python 循环（`build_b1_motion_features`、`x_last_valid_angle` 双重循环等）与"每样本每 epoch 全量重算"模式；预期中等收益，但改动面大、需逐一校验数值一致，须在空闲机器上重测 §1.2 后再定价，不在本轮立即执行。

当前不应为了降低 profiler 中的 CPU 或 kernel 数量而改动 TimeDecoder、Mamba、attention、动态 actor 索引、mode 数或 batch 组织方式。它们属于模型结构、方法定义或数值执行路径，无法在当前证据下承诺"能力和正式结论不变"。

## 3. 执行顺序

### 当前正在运行的实验

不修改正在运行的 M0/M1/M2 训练代码和配置，只处理外部资源：

1. 释放同卡的外部任务；
2. 确认每个训练任务使用独占 GPU；
3. 记录独享状态下的 epoch 时间，作为后续基线。

### 下一轮实验

1. 使用独占 GPU 运行每个 fold；
2. 将 `torch.load` 的 `weights_only` 改为 `True`（§2.2），先校验字段与 loss 一致；
3. 将 `num_workers` 保持为 `4`；
4. 关闭单 GPU 日志的 `sync_dist`；
5. 移除仅用于日志的 `.item()` 同步；
6. 对比优化前后的 epoch 时间、loss 曲线、best epoch 和验证指标。

如果日志、DataLoader 或 `weights_only` 修改导致 batch 内容、loss、指标或 checkpoint 选择异常，立即回退对应修改；GPU 独占可以单独保留。

## 4. 暂不纳入本方案

以下内容当前不做，因此不作为正式实验的提速手段：

- `torch.compile` 或 CUDA Graph；
- 固定 actor padding；
- 增大 batch size 或使用梯度累积；
- 修改学习率、warmup、epoch 数或 optimizer；
- 修改 `bf16` 精度、TF32 或 CUDA kernel；
- 替换 Mamba、RMSNorm、attention 或 Triton 实现；
- 离线重构数据格式；
- `process()` 的循环向量化与预处理落盘缓存（P3，需空闲机器重测定价后另开一轮）。

这些改动可能改变训练动力学、数值执行路径、动态 shape 或数据处理行为，不适合当前"保持模型能力和正式结论不变"的目标。

## 5. 结论

按收益与风险排序，当前值得做的事：

1. **保证 GPU 独占**：已被现有实验直接验证的主提速来源，预计约 `4~6×` 墙钟改善；
2. **`torch.load` 改 `weights_only=True`**：数据管线最大单项，28× 加载加速、零数值风险；
3. **减少日志和同步开销**：风险低、收益次要，作为下一轮工程清理项。

`num_workers` 只用于控制并行实验时的 CPU 资源占用，不是主要加速手段。此前"DataLoader 非瓶颈"的判断已被 §1.2 的数据拆解推翻——数据管线里 `torch.load` 是最大单项，但 GPU 共卡仍是压倒性的主因。独享 GPU 下的其余工程成本来自固定的深层 decoder、Mamba、attention 以及大量小 kernel，但不应通过改模型结构或动态 shape 来处理；模型执行引擎、batch、精度、数据格式改动及循环向量化（P3）暂不进入正式实验。
