# ETH/UCY 训练吞吐瓶颈分析与提速优化方案

_基于 2026-09-05 ~ 09-06 Missing-Aware 第一组筛选实验（M0/M1/M2 × random_fixed4_ng 五折）的实测诊断。_

---

## 1. 现象与实测数据

| 场景 | GPU 占用情况 | 实测速率 | 折算 |
|---|---|---|---|
| 独享卡（启动初期 GPU1 仅本任务） | 单任务 | **~26 s/epoch** | ≈55 ms/step（fold ETH 474 steps） |
| 三任务共卡（GPU1：本任务 + 2 个外部训练） | 3 任务均分 | **~160 s/epoch** | 慢 ~6× |
| 部分共卡（GPU0/GPU3：本任务 + 残留外部任务） | 2 任务 | ~105 s/epoch | 慢 ~4× |

单 variant 五折（100 epochs）耗时：独享约 3.5–4 h，共卡下恶化到 15–20 h。

模型与训练配置事实：DeMo actor-only 仅 **5.7M 参数**，历史序列长度 **8 帧**，batch 64，embed_dim 128，4 层 Mamba（bimamba=true）+ 5 层 Transformer 块 + TimeDecoder；fold ETH train 集 30,307 样本 = 474 steps/epoch。

## 2. 根因分析（按贡献排序）

### 2.1 主因：GPU 共卡竞争（约 6× 损失）

共享服务器上他人任务同卡运行时算力被均分。这是**墙钟问题而非模型问题**——数值结果（同 seed 同数据）不受影响，只影响等待时间。

### 2.2 内因：kernel-launch-bound（小模型 + 碎 kernel）

模型计算量极小（5.7M 参数 × 8 帧序列 × batch 64），但网络由深度串行的小算子组成，GPU 大部分时间花在**等待 kernel 启动**（每次 launch 约 5–20 µs CPU 开销），而不是在计算。类比：发几百趟小车运货，每趟装一点点，时间全耗在起步刹车上。

**诊断证据链**（均为此前轮次实测）：
- SDD（127 steps/epoch）与 ETH/UCY（474 steps/epoch）训练 **it/s 相同** ⇒ 每 batch 成本主导、与数据集规模无关 ⇒ 排除数据 I/O 瓶颈；
- `num_workers` 4→16 无任何变化 ⇒ 进一步排除 I/O；
- GPU util 长期低位（独享时亦仅 ~30%）⇒ GPU 在等 CPU 派发。

### 2.3 放大器：bimamba 双向扫描

双向 Mamba 每块跑正反两次扫描，kernel 数量近乎翻倍——对 2.2 的 launch 开销是放大而非根因（此前单向 Mamba 轮次同样是 launch-bound 量级）。

## 3. 解决方案（分层，按风险递增）

### 第一层：纯调度优化（数值零影响，立即可用）

| 措施 | 预期收益 | 说明 |
|---|---|---|
| 独占卡排期 | 最高 6× | 实测最大头。等空卡/错峰，或多臂分卡并行 |
| 五折分卡并行 | 最多 5× | 一个 variant 的 5 折互相独立，空卡充足时一折一卡 |

### 第二层：CUDA Graph 消灭 launch 开销（收益 2–4×，需等价性验证）

**`torch.compile(mode="reduce-overhead")`**：Inductor 自动融合相邻小算子 + CUDA Graph 把每步几百次 launch 固化为一次回放。社区对小 batch/launch-bound 场景的标准首选（vLLM/SGLang 推理侧同思路），典型 1.5–2×。

前置条件与风险：
1. **必须先固定 actor 维 N**：当前 collate 用 pad_sequence 变长 padding，动态形状导致反复重编译/图断裂。需 pad 到固定 N（如 32）；padding actor 本就被 key_padding_mask 屏蔽，语义不变（非逐位相同）。
2. **mamba_ssm 1.0.1（VideoMamba fork）的自定义 selective_scan CUDA 算子能否被 graph 捕获是最大不确定点**——社区 mamba 用户的老大难，只能实测。
3. **采纳门槛**：同 seed 同数据 compile 前后各训 10 epoch，loss 曲线须在噪声带（±5%）内，否则不进正式协议。

辅助：CSVLogger on_step=True 改 on_epoch（省 5–10%，顺手做）。

### 第三层：加大 batch（吞吐 3–4×，属协议变更而非工程优化）

batch 64→256：launch 次数不变、每步装 4 倍样本 ⇒ steps/epoch ÷4。但**改变训练动态**（有效 lr、收敛轨迹），且打断与已完成轮次的可比性。只能作为"协议 v2"一次性决策：全部 variant（含 M0）重跑 + 重调 lr，不能只给新模型用。

## 4. 已尝试/已否决项

| 项 | 结论 |
|---|---|
| num_workers 4→16 | 无效（非 I/O 瓶颈，实测无变化） |
| Triton fused RMSNorm | **否决**：5880 Ada / CUDA 12.8 驱动不兼容已崩过，已回退 PyTorch 原生 |
| gradient accumulation | 无效：launch 次数不变，治不了 launch-bound |
| 手写融合 kernel | 不做：pointwise 链 compile 免费做；仅跨元素模式（FlashAttention 类）值得手写 |

## 5. 执行建议

1. 正式实验进行中不换执行引擎（中途更换等于换协议）。
2. 下一轮开始前，花半天做第二层 spike：固定 N pad → compile reduce-overhead → mamba 算子捕获实测 → 10 epoch 等价性对照。成功则 26 s/epoch 有望压到 8–12 s/epoch。
3. spike 失败则退回第三层做协议 v2 决策（全量重跑 + lr 重调）。
4. 无论哪条路，正式实验优先争取独占卡窗口（收益最大、零风险）。

## 6. 环境事实附录

- torch 2.2.2+cu121，pytorch_lightning 2.6.5，mamba_ssm 1.0.1（VideoMamba fork，支持 bimamba）
- `torch.compile` 可用（torch ≥2.0）
- 硬件：RTX 5880 Ada ×4（共享服务器，常有外部任务）
- 相关脚本：`scripts/训练与评估/run_missing_aware_ethucy.py`（本轮实验 runner）
