# ETH/UCY 训练吞吐提速方案

_基于 2026-09-05 至 2026-09-06 Missing-Aware 第一组实验（M0/M1/M2、`random_fixed4_ng`）的实测结果。_

## 1. 实测结论

| GPU 状态 | 实测速率 | 结论 |
|---|---:|---|
| 单任务独享 GPU | 约 `26 s/epoch` | 当前基线 |
| 两个任务共卡 | 约 `105 s/epoch` | 慢约 `4×` |
| 三个任务共卡 | 约 `160 s/epoch` | 慢约 `6×` |

当前最主要的问题是 **GPU 共卡竞争**，不是模型结构或数据集规模。fold ETH 训练集有 `30,307` 个样本、每 epoch `474` 个 step；模型约 `5.7M` 参数，batch size 为 `64`。

此前测试还表明：

- `num_workers=4` 调整到 `16` 没有明显提速，DataLoader 不是当前主要瓶颈；
- 独享 GPU 时仍存在一定 CPU dispatch、kernel launch 或同步开销；
- 当前没有足够证据支持直接改模型执行引擎。

## 2. 当前采用的优化

### 2.1 GPU 独占

这是当前收益最高、风险最低的优化，也是正式实验应立即采用的执行方式。

- 一张 GPU 同时只运行一个 DeMo 训练任务；
- 不与 vLLM、其他训练任务或大型推理任务共卡；
- 五折可以并行，但应做到一折一张独占 GPU；
- 启动训练前用 `nvidia-smi` 检查目标 GPU 没有外部进程；
- 不要把多个 fold 挤到同一张 GPU 上。

这只改变任务等待时间，不改变数据、模型、loss、梯度、optimizer 更新或 checkpoint 选择，因此不改变模型能力和正式实验结论。

**已观测收益**：从共卡恢复到独享，墙钟时间预计改善约 `4~6×`。

### 2.2 减少日志同步开销

当前训练每个 batch 记录多个 loss，并在单 GPU 下使用 `sync_dist=True`。`cal_loss()` 还会多次调用 `.item()` 生成日志标量，这可能造成不必要的 GPU-CPU 同步。

下一轮训练可以做以下工程修改：

- 单 GPU 训练将训练日志的 `sync_dist` 改为 `False`；
- 减少 step 级日志，优先保留 epoch 级日志；
- 保留 loss 计算和返回给 Lightning 的 tensor，不让日志值参与 loss 或梯度计算；
- 移除仅用于日志的 `.item()` 同步，但保留相同的日志字段；
- 保留 `val_minFDE6` 监控和 best/last checkpoint 逻辑。

这类修改只影响日志和同步，不改变模型前向、loss 数值定义或反向传播。

**预期收益**：小到中等，具体收益需要在独享 GPU 上实测；它不是当前主要的 `4~6×` 加速来源。

### 2.3 降低 DataLoader 资源争抢

虽然 DataLoader 不是当前主要瓶颈，但多个训练任务并行时，`num_workers=16` 会造成不必要的 CPU 和内存争抢。下一轮建议：

- 将单任务 `num_workers` 设为 `4` 或 `8`；
- 多任务并行时优先使用 `4`；
- 保持 `pin_memory=True`；
- 不改变 sampler、shuffle、batch size 和样本处理逻辑。

这项优化主要用于减少多任务环境的资源争抢，不应预期显著提升独享 GPU 下的单任务速度。

## 3. 执行顺序

### 当前正在运行的实验

不修改正在运行的 M0/M1/M2 训练代码和配置，只处理外部资源：

1. 释放同卡的外部任务；
2. 确认每个训练任务使用独占 GPU；
3. 记录独享状态下的 epoch 时间，作为后续基线。

### 下一轮实验

1. 使用独占 GPU 运行每个 fold；
2. 将 `num_workers` 控制在 `4~8`；
3. 关闭单 GPU 日志的 `sync_dist`；
4. 移除仅用于日志的 `.item()` 同步；
5. 对比优化前后的 epoch 时间、loss 曲线、best epoch 和验证指标。

如果日志或 DataLoader 修改导致 batch 内容、loss、指标或 checkpoint 选择异常，立即回退对应修改；GPU 独占可以单独保留。

## 4. 暂不纳入本方案

以下内容当前不做，因此不作为正式实验的提速手段：

- `torch.compile` 或 CUDA Graph；
- 固定 actor padding；
- 增大 batch size 或使用梯度累积；
- 修改学习率、warmup、epoch 数或 optimizer；
- 修改 `bf16` 精度、TF32 或 CUDA kernel；
- 替换 Mamba、RMSNorm、attention 或 Triton 实现；
- 离线重构数据格式。

这些改动可能改变训练动力学、数值执行路径、动态 shape 或数据处理行为，不适合当前“保持模型能力和正式结论不变”的目标。

## 5. 结论

当前最值得做的只有两件事：

1. **保证 GPU 独占**：这是已被现有实验直接验证的主要提速来源，预计可带来约 `4~6×` 墙钟改善；
2. **减少日志和同步开销**：风险低，但收益次要，作为下一轮工程清理项。

`num_workers` 只用于控制并行实验时的 CPU 资源占用，不是主要加速手段。其余模型执行引擎、batch、精度和数据格式改动暂不进入正式实验。
